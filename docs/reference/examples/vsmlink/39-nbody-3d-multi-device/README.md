# 39-nbody-3d-multi-device: MN-Core2 を複数枚使う 3D N 体（他粒子は各デバイスの DRAM から @broadcast で受ける）

粒子を複数のデバイスに分けて、全対全の重力計算を回す example。実機は **2 枚で 8192 粒子、4 枚で 16384 粒子**（1 枚あたり 4096 粒子、1 PE が 1 粒子）。

- 8192 粒子を 2 つに分け、4096 粒子ずつを各 MN-Core2 に割り当てる
- **各タイムステップで、2 枚が出した結果（4096 × 2）をホストが回収して 8192 粒子の並びにし、両方のデバイスの DRAM へ入れ直す。これを繰り返す**
- 他粒子（8192 個）は、各デバイスの DRAM から `@broadcast` で受ける（`.param` の `:place :group-dram`）
- デバイス同士は直接つながらない。**デバイスの間のデータの移動は、ホストだけが行う**

`examples/28-nbody-3d`（他粒子を PDM から読む）に、`examples/38-nbody-4096-dram`（他粒子を DRAM から読む）の方式と、複数枚への分割を足した。
2 枚が見える実機では、**Plummer 星団 2 個（4096 + 4096）の衝突を 2000 タイムステップ流し、mp4 にする**ところまで行える（`ninja run-device`、`make_mp4.py`）。
emu:lib は、デバイス 1 枚、N=32 だけである（emu:lib ではデバイス 2 枚を使えない）。

## データの移動

**どのデータを、誰が動かすか**を、担当ごとに分けて書く。

| 担当 | 動くデータ | 向き | 場所と番地 |
|---|---|---|---|
| **host-dma の API**（`mnc2_send` / `mnc2_recv`） | 初期値、毎タイムステップの全粒子の並び、更新後の位置と速度 | ホスト ↔ **PDM0**（デバイスごと）| 下の「PDM0 の配置」。番地は u64 単位（byte は × 8）。ホストが DRAM に直接送る API は無い |
| **`_vsm` に直接書いた `mvp`**（directive ではない。stage kernel） | 全粒子の並び `[x,y,z,m] × N` | PDM0 → **全グループ（0〜3）の DRAM**（デバイスごと）| PDM0 の 262144 番地から、各グループの DRAM の 0 番地から。`$p262144@0` → `$d0@<g>` |
| **directive が自動で行う** | `@distribute`（init）: PDM0 → PE。`@broadcast`（init の定数）: PDM0 → PE。`@broadcast`（accumulate）: **DRAM** → L2BM → L1BM → PE。`@collect`: PE → PDM0 | 各 directive の仕様書の節 | slot の `:place` と `:addr`（下の「slot」）|
| **ホスト（C のプログラム）** | 2 枚の結果を集めて全粒子の並びにし、2 枚へ送り直す | デバイス 0 ↔ ホスト ↔ デバイス 1 | 粒子 `d × B + i` は、デバイス d の PE i の値（下の「粒子の割り当て」）|

**PDM0 は、グループ 0 の PDM である**（dev manual の `$p<addr>@0`。`param-spec.md` の `:place`）。
DRAM はグループごとに別のメモリで、`$d<addr>@<g>` の `<g>` で選ぶ。stage kernel は、4 つのグループの DRAM に同じ値を置く。

1 タイムステップの流れ（2 枚のとき）:

```
デバイス 0: kick → drift → collect_pos ──┐                         ┌─ stage → accumulate x64 → kick → collect_vel ─ 速度を回収
                                          ├→ ホストが位置を回収 →   ┤
デバイス 1: kick → drift → collect_pos ──┘   8192 粒子の並びにして   └─ stage → accumulate x64 → kick → collect_vel ─ 速度を回収
                                              両方の PDM0 へ送る
                                              (stage が全グループの DRAM へ置く)
```

### 粒子の割り当て

粒子の数を N、デバイスの数を D、1 枚あたりの粒子の数を B = N / D とする（B は 4096 以下）。

- **デバイス d の PE i（0 ≤ i < B）は、粒子 `d × B + i`** を担当する。位置・速度・加速度は、その PE の LM に残る
- B が 4096 より小さいとき、残りの PE（i ≥ B）には、そのデバイスの先頭の粒子の複製を入れる（計算は無視するが NaN を避ける）
- `accumulate` は、全 N 粒子を、粒子の番号の順に、DRAM から読む。**足し込みの順序は、デバイスの分け方に依らない**

### PDM0 の配置（デバイスごとに同じ。u64 単位、byte は × 8）

| 番地 | 大きさ | 内容 | 並び | 書く担当 | 読む担当 |
|---|---|---|---|---|---|
| 0 | 16384 | 担当する粒子の初期の位置と質量（x,y,z,m） | 成分ごと（各 4096 PE） | ホスト（1 回） | `@distribute`（init、slot 8）|
| 16384 | 64 | 定数（eps2、0.5、1.5、dt） | — | ホスト（1 回） | `@broadcast`（init、slot 16）|
| 40960 | 12288 | 担当する粒子の初期の速度（vx,vy,vz） | 成分ごと（各 4096 PE） | ホスト（1 回） | `@distribute`（init、slot 24）|
| 131072 | 12288 | 更新後の位置 | 成分ごと（各 4096 PE） | `@collect`（collect_pos、slot 8） | ホスト（`mnc2_recv`）|
| 143360 | 12288 | 更新後の速度 | 成分ごと（各 4096 PE） | `@collect`（collect_vel、slot 8） | ホスト（`mnc2_recv`）|
| **262144** | 4N を 64 の倍数に切り上げ（N=32 で 128、N=8192 で 32768） | **全粒子の並び** | 粒子ごと `[x,y,z,m]` | ホスト（毎タイムステップ） | **stage kernel の `mvp`** |

`examples/28-nbody-3d` や `examples/38-nbody-4096-dram` では全粒子の並びを 20480 番地に置いているが、N=8192 では 20480〜53247 になり、40960 番地の速度の置き場と重なるので、262144 番地に移した。

### 各グループの DRAM の配置（デバイスごと、4 つのグループで同じ。u64 単位）

| 番地 | 大きさ | 内容 | 書く担当 | 読む担当 |
|---|---|---|---|---|
| 0 | 4N を 64 の倍数に切り上げ | **全粒子の並び** `[x,y,z,m] × N` | stage kernel の `mvp`（PDM0 の 262144 番地から） | `@broadcast`（accumulate、slot 8）|

accumulate の分割 kernel `g`（粒子 `128g`〜）の slot 8 は `:addr` が `4 × 128g` で、その kernel の実行ごとに、この番地から続きを読む。

### slot

| kernel | slot | `:place` | `:addr`（u64） | タグ |
|---|---|---|---|---|
| init | 8（位置の `@distribute`） | `:pdm0` | 0 | 送信 `#x10` |
| init | 16（定数の `@broadcast`） | `:pdm0` | 16384 | — |
| init | 24（速度の `@distribute`） | `:pdm0` | 40960 | — |
| accumulate の分割 `g` | 8（他粒子の `@broadcast`） | **`:group-dram`** | `4 × 128g` | **付けない**（付けると E277）|
| collect_pos | 8（`@collect`） | `:pdm0` | 131072 | 受信 `#x1e` |
| collect_vel | 8（`@collect`） | `:pdm0` | 143360 | 受信 `#x1f` |
| stage | なし（directive を使わない） | — | — | `.param` の予約タグ `#x3f`（vsmlink 用）と `#x3e`（`mvp` の完了待ち）|

## stage kernel

`gen_stage.py` が生成する `_build/stage_n<N>._vsm` は、`mvp` を直接書いた `_vsm` である。1 回の `mvp` は 4096 u64 以下に分ける。

```
	mvp/n4096i3e $p262144@0 $d0@0     # PDM0 の 262144 番地から、グループ 0 の DRAM の 0 番地へ
	nop/3
	nop; wait i3e
	nop/5
	...                               # グループ 0〜3、4096 u64 ごとに繰り返す（N=8192 は 4 グループ × 8 回）
```

- タグ付きの `mvp` には、同じタグ（`i3e`）の `wait` を置く。`wait` がそのタグの完了の印を消費するので、続けて同じタグを使える。
  `wait` を置かないタグ付きの MV 命令があると、印が残り、あとの同じタグの `wait` が転送の終わる前に抜ける
- `wait` の後の `nop/5` は、host-dma の examples（`mv-p10.vsm` など）と同じ形である
- stage kernel は、ホストの `mnc2_send` が終わってから exec する。`mnc2_send` は転送が終わってから戻るので、送信のタグは要らない

## この example でできること

粒子数 N と使うデバイスの数 D（`--devs=` に並べる番号の数）は、**N が D で割り切れ、N / D が 4096（1 デバイスの PE 数）以下**であれば選べる。
N はホストのビルド時に決まり（`-DUNROLL`）、D と番号は実行時に決まる。

| やりたいこと | 方法 | 実機で確かめた結果 |
|---|---|---|
| 1 枚で小さい N の値照合（emu:lib も可） | `ninja test-emu-lib`、`ninja test-device`（N=32） | PASS |
| 1 枚で N=4096 の値照合 | `ninja test-device-n4096` | PASS |
| 分け方を変えても、結果がバイト単位で同じことの確認 | `ninja compare-split-device`（N=4096、1 枚と 2 枚）。N=32 は 1 枚と 4 枚も一致した | 一致 |
| 2 枚で N=8192 | `ninja test-device-n8192`（4 タイムステップ）、`ninja run-device`（2000 タイムステップ） | PASS |
| 4 枚で N=16384 | `ninja test-device-n16384`（4 タイムステップ）、`ninja run-device-n16384`（2000 タイムステップ） | PASS（4 タイムステップ、2000 タイムステップとも）|
| 結果から mp4 を作る | `python3 make_mp4.py <結果のディレクトリ> <出力.mp4>` | N=8192、N=16384 で作れた |
| 任意の初期条件で回す | ホストの第 1 引数に `<ic.bin>`（1 粒子 8 double の struct 形）を渡す。Plummer 星団は `gen_ic_plummer.py` | — |
| 別の N（例: N=12288 を 4 枚で、1 枚あたり 3072） | `gen_chunks_ninja.py` の `NS` に N を足して再生成し、`build.ninja` にホストと target を足す。既にある N のホストは、`--devs=` を変えるだけで枚数を変えられる（例: `_build/nbody_n8192 --devs=0,1,2,3` は 1 枚あたり 2048 粒子） | — |

できないこと: 1 枚あたり 4096 粒子を超える分け方（4 枚で N=16384 が上限）。emu:lib では、N=4096 以上と、デバイス 2 枚以上（emu:lib はデバイス 0 だけが開ける）。

## 使い方

```bash
# SDK を有効にし、この example のディレクトリで実行する（examples の README.md の「動かし方」）

ninja                             # vsmlink が accumulate 分割 0（N=32）を生成する
ninja build-e2e                   # + assemble3 + ホストのビルド（N=32）
ninja test-emu-lib                # emu:lib で N=32、4 タイムステップ（デバイス 1 枚。値照合）
ninja test-device                 # 実機で N=32、デバイス 1 枚（lit 用）
```

実機で手動（2 枚が見える環境。名指ししたときだけ build される）:

```bash
ninja test-device-n4096           # N=4096、デバイス 1 枚で値照合
ninja compare-split-device        # N=4096 を、デバイス 1 枚と 2 枚（1 枚あたり 2048）で回し、バイト単位で一致すること
ninja test-device-n8192           # N=8192、デバイス 2 枚で値照合（4 タイムステップ）
ninja run-device                  # N=8192、デバイス 2 枚で星団 2 個の衝突を 2000 タイムステップ
ninja test-device-n16384          # N=16384、デバイス 4 枚で値照合（4 タイムステップ）
ninja run-device-n16384           # N=16384、デバイス 4 枚で星団 2 個の衝突を 2000 タイムステップ
```

ホストは単体でも動かせる。

```
_build/nbody_n8192 [<ic.bin>] [--devs=<n>,<n>] [--every=<n>] [--verify=<n>] [--monitor=<n>] [--vel] [--out=<dir>] [--show-flags]
```

| 引数 | 意味 |
|---|---|
| `<ic.bin>` | 初期条件（struct 形バイナリ。1 粒子 8 double）。省略時は `_build/ic_collide_n8192.bin`（Plummer 星団 2 個）|
| `--devs=<n>,<n>` | 使うデバイスの番号（最大 4 枚）。省略時は N=16384 で `0,1,2,3`、N=8192 で `0,1`、N=32 と 4096 で `0`。デバイスの数は N を割り切り、1 枚あたり 4096 以下であること |
| `--every=<n>` | n タイムステップごとに位置を記録する。既定 1 |
| `--verify=<n>` | 先頭 n タイムステップだけ host 倍精度と位置を照合する（総タイムステップ数と同じときだけ最終状態と比べる）。既定 0 |
| `--monitor=<n>` | n タイムステップごとに保存量を `run.json` に記録する。既定 1、0 で無効 |
| `--vel` | 速度のスナップショット（`vel_<NNNN>.bin`）も出す。分け方の比較に使う |
| `--out=<dir>` | 結果を出すディレクトリ。既定は `_result_n<N>` |
| `--show-flags` | 成功しても、到達した段階と情報のビットを出す |

出力は `_result_n<N>/` に、`pos_<NNNN>.bin`（粒子ごとに `x,y,z` の double。128 コマで次のファイル）、`run.json` が書かれる。
ファイル名に日時を含めない（実行の前に、出力のファイル名が決まっているため）。

## 実機での確認

実機の環境で、次の順で行う（結果は下の「確かめた範囲」）。実機の環境では `/opt/mncore2-sdk/bin/sdk-examples vsmlink` で examples をコピーして使う。
**1 はデバイス 1 枚でよい。2 から 4 は 2 枚、5 と 6 は 4 枚が見える環境で**（`gpfn3-smi` で枚数を確かめる。デバイス 1 が開けないと `NG_OPEN` で終わる）。

```bash
cd <コピーした examples>/39-nbody-3d-multi-device
source /opt/mncore2-sdk/bin/activate
```

1. **デバイス 1 枚、N=4096、値照合**: `ninja test-device-n4096`（4 タイムステップ、ホスト倍精度との照合）。stage kernel と DRAM の経路の確認になる。
2. **デバイスの分け方の比較**: `ninja compare-split-device`。N=4096 を、デバイス 1 枚（1 枚あたり 4096）と、2 枚（1 枚あたり 2048）で回し、
   `pos_*.bin` と `vel_*.bin` がバイト単位で一致すること。**割り当ての番号のずれ、片方のデバイスの結果が古いままになる誤りは、
   許容誤差つきの照合では見えず、ここで見える**
3. **N=8192、デバイス 2 枚、短い実行**: `ninja test-device-n8192`（4 タイムステップ、ホスト倍精度との照合）。
   **kernel 64 個 × 2 枚の load が通るか**をここで確かめる。通らなければ、分割 kernel を、使う分だけ load → exec → free する形に変える
4. **星団 2 個の衝突、2000 タイムステップ**: `ninja run-device`。エネルギー保存、運動量・重心、half-mass radius が `run.json` に記録される。

   ```bash
   # 結果を手元へ回収したあと
   python3 make_mp4.py _result_n8192 collision.mp4 --fps=30            # 全体が見える枠
   python3 make_mp4.py _result_n8192 collision_zoom.mp4 --fps=30 --lim=4   # 核が大きく見える枠
   ```

   実機の環境に `ffmpeg` や matplotlib が無いときは、`_result_n8192/` を手元へ運んで実行する。出力は約 40 MB なので、転送が途中で切れるときは、
   `tar czf - pos_0000.bin pos_0001.bin run.json | split -b 5M - part_` で 5 MB ずつに分けて運ぶ。

   `ic_collide_n8192.bin` の `--sep=6 --vrel=0.8` は目安で、実機で見て調整する（`gen_ic_plummer.py` の引数）。
5. **N=16384、デバイス 4 枚、短い実行**: `ninja test-device-n16384`（4 タイムステップ、ホスト倍精度との照合）。
   kernel 128 個 × 4 枚（合計約 740 MB）の load が通るかをここで確かめる。
6. **星団 2 個の衝突、2000 タイムステップ（4 枚）**: `time ninja run-device-n16384`。結果は `_result_n16384/`。mp4 は 4 と同じく `make_mp4.py` で作る。

## 書くときに知っておくこと

- `@broadcast` の slot を `:group-dram` にするときは、`.param` に `:send_wait_tag` を書かない（E277）。DRAM へ置くのはホストではなく stage kernel だからである
- 各グループの DRAM に置く値は、グループごとに違ってよい。`@broadcast` は、各 PE に**自分のグループの DRAM の値**を渡す。この example は 4 つのグループに同じ値を置くので、全 PE が同じ他粒子を受け取る
- kernel は、デバイス非依存かどうかが公開文書で確かめられないので、**デバイスごとに load する**。N=8192 では 1 枚あたり約 92 MB（1 つ約 1.44 MB × 64）、2 枚で約 184 MB になる。N=16384 では 1 枚あたり約 184 MB（× 128）、4 枚で約 740 MB になる
- kernel を積む順序は単純にしてある（デバイス 0 に積み切ってから、デバイス 1、2、3 の順に積む）。複数のデバイスを止めずに交互に積む工夫は、正しさを確かめたあとの課題である
