# 33-broadcast-soa2aos: レイアウト変換を挟んでループを閉じる

`broadcast → 計算 → soa2aos → collect` を 1 タイムステップとして、ダブルバッファで 2 回まわす。
**device 上だけでループが閉じること**と、**レイアウト変換がどの並びを PDM に置くか**を確認する。

並びは `--show-order` で実際に出せる（「レイアウト変換のたびに PDM がどう並ぶか」の節を参照）。
**このループでは毎ステップ同じ順列がかかり、元には戻らない。** `examples/30-soa2aos` は
2 回で戻るが、それはレイアウト変換の前段が違うためである。

`examples/30-soa2aos` はレイアウト変換単体（PDM から読んで PDM へ書く）の確認で止まっており、その出力を
`@broadcast` で読み直すところまで繋がっていなかった。ここでそれを繋ぐ。

## なぜレイアウト変換が要るのか

**`@collect` が書く並びと、`@broadcast` が読む並びが違う。**

```
成分ごと (SoA) — @distribute / @collect が扱う形
  番地:  0       1       2     ...  4095    4096    4097  ...  8191    8192 ...
  中身:  x[0]    x[1]    x[2]  ...  x[4095] y[0]    y[1]  ...  y[4095] z[0] ...
         └─────────── x を 4096 個 ────────┘└────── y を 4096 個 ──────┘

粒子ごと (AoS) — @broadcast が扱う形
  番地:  0       1       2       3       4       5       6       7       8 ...
  中身:  x[0]    y[0]    z[0]    m[0]    x[1]    y[1]    z[1]    m[1]    x[2] ...
         └───── 粒子 0 ─────┘   └───── 粒子 1 ─────┘   └── 粒子 2 ...
```

計算結果を `@collect` で PDM に書くと成分ごとに並ぶが、次のタイムステップの `@broadcast` は
粒子ごとの並びを要求する。**このままでは 1 回目から形式が合わずループが閉じない。**

この example で実際に確認できる（`ninja test-emu-lib-plain`）。レイアウト変換なしの場合、`@collect` の
出力を粒子ごとの並びとして読むと `m` の位置に `x` の値が出る。

従来はホストが回収して詰め替えて送り直していた。**レイアウト変換を device 上で行えば、この往復が
丸ごと消える。**

## PDM のメモリマップ

| 番地 (u64) | サイズ | 内容 | 並び | 誰が書く | 誰が読む |
|---|---|---|---|---|---|
| 0 | 16384 | 初期値 | 成分ごと | ホスト（1 回だけ）| `@distribute`（init） |
| 20480 | 16384 | BUF0 | 粒子ごと | ホスト（初回）と `@collect` | `@broadcast` |
| 40960 | 16384 | BUF1 | 粒子ごと | `@collect` | `@broadcast` |

**`@distribute` は init の 1 回だけ。** PE は自分の担当する値を LM に持ち続けるので、配り直す
必要がない。各タイムステップで要るのは「更新後の値を全 PE へ配れる形で PDM に置き直す」ことで、
それがレイアウト変換の役目になる。

**ダブルバッファ**にして、読み元と書き先を交互に入れ替える。

```
BUF0 → (broadcast → 計算 → soa2aos → collect) → BUF1
BUF1 → (broadcast → 計算 → soa2aos → collect) → BUF0
```

## LM のレジスタ割り当て

| レジスタ | 用途 |
|---|---|
| `$lm0` | x（計算対象）|
| `$lm2` | y（計算対象）|
| `$lm4` | z（計算対象）|
| `$lm6` | **m = PE ID。計算では触らない** |
| `$lm8, 10, 12, 14` | **レイアウト変換の出力先。計算では使えない** |
| `$lr16, 18, 20, 22` | broadcast の着地（他粒子の x, y, z, m）|

**レイアウト変換は入力と出力に別々の連続 4 本を要求する**ので、`$lm0..6` を入力、`$lm8..14` を出力に
固定して衝突を避ける。計算部分の `._vsm` はこの約束に従う。

## N=64 の意味 — **粒子数ではなく、1 ステップに broadcast する要素数**

`N` は 64 だが、**4096 PE すべてに値が入っている**（`m` に PE ID 0..4095 を入れてある）。
`N` は「1 ステップで `@broadcast` を何個並べるか」であって、系に存在する要素の数ではない。

**ここが N 体のアプリと違う。** あちらの `N` は実在する粒子の数で、
`N < 4096` のときは残りの PE に粒子 0 の複製が入る。レイアウト変換後の位置 0..N-1 には
`4*(k%1024)+k/1024` 番の要素が来るので、`N=32` なら 0, 4, 8, ..., 124 を指す。
**実在するのは 8 個だけ**になり、力の評価が壊れる。

| | `N` の意味 | レイアウト変換後に位置 0..N-1 を読むと |
|---|---|---|
| 33（このループ）| broadcast する個数。**全 PE に値がある** | 4096 個のうち N 個。**すべて実在する** |
| N 体のアプリ | 実在する粒子数 | 実在しないものを掴む（`N < 4096` のとき）|

**全 PE に値があるかどうか**で、レイアウト変換後に先頭から読んでよいかが決まる。33 は読んでよく、
N 体は読めない（N 体のアプリでは `accumulate` が、レイアウト変換後の位置に合わせて、粒子番号の
4 の余りごとに 4 つの slot の続きを読む）。

## 順列 — レイアウト変換は粒子の並びを入れ替える

`dmwrite` / `dmread` は MAB 内の **4 PE × 4 アドレス**を転置する。1024 MAB が同時に動くので、
全体では次の対応になる。

**レイアウト変換後の位置 `k` には、元の粒子 `4g + i` が来る**（`k = 1024i + g`）。

| レイアウト変換後の位置 k | 元の粒子番号 | 導出 |
|---|---|---|
| 0 | 0 | i=0, g=0 → 4·0+0 |
| 1 | 4 | i=0, g=1 → 4·1+0 |
| 2 | 8 | i=0, g=2 → 4·2+0 |
| 3 | 12 | i=0, g=3 → 4·3+0 |
| … | | |
| 1023 | 4092 | i=0, g=1023 |
| 1024 | 1 | i=1, g=0 → 4·0+1 |
| 1025 | 5 | i=1, g=1 → 4·1+1 |
| … | | |
| 4095 | 4095 | i=3, g=1023 → 4·1023+3 |

**この対応は実測で確認してある。** `m` に PE ID（0〜4095）を入れ、計算では触らずに素通しさせて
いるので、回収した `m` の並びを見れば順列が分かる。

**並びの式と注意は `share/vsmlink/directives-spec.md` の「@distribute_aos2soa / @collect_soa2aos」にまとめてある。**

### レイアウト変換のたびに PDM がどう並ぶか — **毎ステップ同じ形でかかる。累積しない**

**以前このファイルには「レイアウト変換は対合なので 2 回で元に戻る」と書いてあったが、誤りだった。**
このループでは**毎ステップ同じ順列がかかり、元には戻らない**。

`--show-order` で実際の並びを出せる。

```
$ ./_build/bcast_soa2aos --show-order

  step 0 の collect 出力 (位置 k にある m = 元の要素番号):
           k      0      1      2      3      4      5      6      7   1024   1025   2048   3072   4095
           m      0      4      8     12     16     20     24     28      1      5      2      3   4095
  step 1 の collect 出力 (位置 k にある m = 元の要素番号):
           k      0      1      2      3      4      5      6      7   1024   1025   2048   3072   4095
           m      0      4      8     12     16     20     24     28      1      5      2      3   4095
```

**2 つのステップで完全に同じ**である。

### なぜ `examples/30-soa2aos` では 2 回で戻るのか

30 は**戻る**（実測でバイト一致）。同じ命令（`dmwrite`/`dmread`）を使っているのに結果が違うのは、**前段が違う**
からである。

| | レイアウト変換にかける値の出どころ | 2 回適用すると |
|---|---|---|
| `examples/30` | **`@distribute` で PDM から読み直す** | **元に戻る** |
| このループ（33）| `$lm0..6` の常駐値（`init` で 1 回配ったあと計算が更新）| **戻らない。毎回同じ順列** |

30 は「PDM の並び」に変換をかけるので、2 回かければ変換が 2 回積み重なる。
**レジスタ上の 4x4 入れ替えは 2 回で元に戻る**（行列の転置と同じ）ので、積み重ねると
打ち消し合う。

**並びの式は `share/vsmlink/directives-spec.md` の「@distribute_aos2soa / @collect_soa2aos」にある。** 同じ事実の説明を
複数の場所に置くと食い違うので、ここには書かない。位置の対応 `perm_src` の巡回長は
位置ごとにばらばら（1, 2, 3, 6）で、すべてが戻るまでには 6 回かかる。

33 は違う。**常駐値は PDM から読み直していない。** 「PE p が要素 p を持つ」という対応は
計算しても変わらないので、`@collect` が書く並びは毎ステップ同じになる。前のステップの
並びは引き継がれない。

**`dmwrite`/`dmread` そのものは同じでも、PDM に何が並ぶかは前段で決まる。**

### 見る位置を間違えないこと

```
perm_src(k) = 4*(k % 1024) + k / 1024
```

**k < 1024 では単に 4k になる。** 位置 1 に要素 4 が来るので、先頭だけを見ても並べ替えが
かかっていることは分かる。ただし、先頭 1024 個だけでは単純な 4 刻みに見え、式の `k / 1024` の
項は表れない。上の出力に `1024, 1025, 2048, 3072, 4095` を入れてあるのはそのためである。

**先頭数個だけを見て判断すると誤る。** 実際に N 体のアプリを作るとき、
先頭だけを見て「対合だ」と誤認し、値が合わない原因を長く取り違えた。

### ホスト側の `permuted_input` は 2 ステップ限定

ホストは `step % 2 == 1` のときだけ「入力に順列がかかっている」として照合している。
これは**このループが 2 ステップしか回さないから**成り立っている。

```
step 0 の broadcast が読むのは  ホストが書いた AoS      → 順列なし
step 1 の broadcast が読むのは  step 0 の collect 出力  → 順列あり
```

**3 ステップ以上に増やすと壊れる。** step 2 が読むのも device の collect 出力なので順列は
かかったままだが、`step % 2 == 0` では「順列なし」と判定してしまう。正しくは
「step 0 だけ順列なし、それ以降は順列あり」である。

### 順列は計算に影響するか

**全対全の合算のように順序に依存しない計算なら無害。** 足す順番が変わるだけで結果は同じである。
ただし **2 回目の broadcast が読む順序は変わる**ので、ホスト側で照合するときはそれを織り込む
必要がある（device が j 番目に読むのは粒子 `4g+i`）。

**粒子に紐づく量は一緒に動かすこと。** 位置だけレイアウト変換して質量を置き去りにすると対応が壊れる。

## 1 kernel = 16 粒子 = 1 転送

`@broadcast` は 1 回の転送（`mvb`）で **64 u64 = 16 粒子ぶん**を L1BM に移動するが、1 回の
`@broadcast` が PE へ配るのは 4 u64（1 粒子ぶん）である。**同じ slot の `@broadcast` は、
L1BM に移動した 64 u64 の続きを消費し、使い切るまで転送が出ない。**

```
mvb 1 回 → L1BM に 16 粒子ぶんが載る
  @broadcast  1 回目 → 粒子 0 を配る（転送あり）
  @broadcast  2 回目 → 粒子 1 を配る（転送なし）
  ...
  @broadcast 16 回目 → 粒子 15 を配る（転送なし）
  @broadcast 17 回目 → 粒子 16 を配る（次の 64 u64。転送あり）
```

実測（`ninja measure`）:

```
4096 粒子 (1 kernel)       mvb=256 l1bmp=4096
```

**4096 粒子を読むのに転送は 256 回。** 16 粒子ごとに 1 回で、これが下限である。

この example は **1 kernel = 16 粒子（1 回の転送ぶん）** で刻んである（`CHUNK=16`）。生成される kernel が
「PDM から 1 回転送し、その 16 粒子を配る」という 1 対 1 の対応になり、仕組みがそのまま読める。

### 刻み方は性能とのトレードオフ

**刻み数を変えても転送の合計回数も命令数も変わらない。** 変わるのはホストからの呼び出し回数で、
ここに性能差が出る。

| 刻み | kernel 数 | ホストからの `load` / `exec` | 性質 |
|---|---|---|---|
| 16 粒子（この example）| 256 | 多い | **仕組みが読める** |
| 128 粒子（N 体のアプリ）| 32 | **1/8** | 実行が速い |

**example は仕組みを見せるので前者、apps は実行するので後者**を採っている。同じ処理でも目的が
違えば刻み方が変わる、という例になっている。

なお **16 の倍数でなければ転送が分割をまたぐ**ので、刻み幅は 16 の倍数にすること
（`gen_step.py` が検査する）。

## 計算部分は差し替えられる

骨格（broadcast → 計算 → レイアウト変換 → collect）と計算の中身を分離してある。`gen_step.py` が
計算の `._vsm` を骨格に挟み込むので、別の計算に差し替えられる。

### `rotate._vsm`（既定）

2 次元回転。`x' = x·c − y·s`、`y' = x·s + y·c`。c, s は broadcast で読んだ他粒子の x, y を
使う（初期値を単位円上に取ってあるので `c² + s² = 1`）。

**ノルムを保つので発散も収束もしない。** 丸め誤差が蓄積しないため、タイムステップを増やしても
ホストとの照合が安定する。実測で `max_rel = 2.036e-14`。

### `logistic._vsm`（未解決）

ロジスティック写像 `x' = r·x·(1−x)`。**現在 device 側で値が `inf` になり動いていない。**
下記「未解決」を参照。

## 実行

```bash
source scripts/overlay

ninja                      # vsmlink (.vsm 生成)
ninja build-e2e            # + assemble3 + host C
ninja test-emu-lib         # レイアウト変換あり、2 タイムステップ (これが本命)
ninja test-emu-lib-plain   # レイアウト変換なし、1 タイムステップ (形式が合わないことの確認)
ninja measure              # 転送回数を数える (実行しない。生成物を grep するだけ)
```

emu:lib で回すのは **N=64（4 分割）**。1 kernel = 16 粒子で刻むと N=4096 では 256 分割になり、
emu:lib での実行が現実的でなくなる。仕組みの確認は少ない粒子数でできるので CI は N=64 とし、
転送回数の測定だけ N=4096 の単一 kernel で行う。

## 書くときに引っかかった制約

### 演算の 2 入力は別のメモリ系統から取る

```asm
dvadd $ln0 -$ln2 $ln4     # NG: lm1 と in_lm1 の命令フィールドが衝突する
dvadd $ln0 -$ls0 $lr0     # OK: LM1 と LM2
```

assemble3 が `Instruction field conflict detected between 'lm1' and 'in_lm1'` で拒否する。
積を LM1 と LM2 に振り分けてから足す形にする。

### 分割 kernel に `send_wait_tag` を付けない

ホストが送るのは 1 タイムステップ目だけで、2 回目以降は device の `@collect` がその領域を書く。
kernel 内で送信完了を待つ形にすると **2 回目の待ちが解けない**。1 回目ぶんの送信完了は
ホストが `mnc2_wait_idma_idle` で待ってから exec する。

なお init と分割 kernel で同じ wait tag を使うと
`PE waits for double asserted DMA done flag` になる。

## 未解決

**`logistic._vsm` が動かない。** device 側で値が `inf` になる。

- ホスト側の倍精度計算では、係数 3.9 で 64 回適用しても値は 0.82 前後に収まる
- 係数を 4.0 から 3.9 に下げても解消しない（4.0 は写像の最大値がちょうど 1.0 に達し、
  丸め誤差で 1 を超えると `1−x` が負になって発散するため、それ自体は避けるべき）
- 定数 1.0 を置くレジスタを broadcast の着地や結果の置き場と分離しても解消しない

**計算部分を差し替えられること自体は `rotate` で確認できている**（同じ骨格に別ファイルを
差し込んで生成・ビルドできている）。logistic はその追加確認用だったので、未解決のまま残す。

`ninja test-emu-lib-log` で再現する。
